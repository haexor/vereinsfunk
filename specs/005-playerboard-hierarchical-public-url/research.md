# Research: Hierarchische öffentliche PlayerBoard-URLs

Findings come from reading the current code on `main` at `fc7ba42` (migration `2026111701_public_playerboard_display.sql` is the latest). Confidence tags: **[Certain]** read in code, **[Likely]** strong inference, **[Guessing]** needs a check during implementation.

## Current state

- `playerboard_settings.public_slug` is generated by trigger `playerboard_settings_public_slug_generated` as `<dept ≤20>-<team ≤20>-<team uuid>`. Uniqueness is `unique (organization_id, public_slug)`. **[Certain]**
- `departments.slug` already exists, is unique per organization, is set once by `create_department()` and is not touched by `PATCH /v1/departments/:id` (rename changes only `name`). It has no format or length constraint. **[Certain]**
- `teams` has no slug and no uniqueness on `name`. **[Certain]**
- Public resolution is `authz.playerboard_public_team(org_slug, team_slug)`, used by six `public.playerboard_public_*` functions. They are called only from `apps/api/src/routes/playerboard/public.ts`. **[Certain]**
- The auth middleware lets exactly `/mannschaft/<slug>/<slug>` through (`isPublicTeamPagePath`, path length ≤ 200). **[Certain]**
- The settings API builds `publicPath` as `/mannschaft/${orgSlug}/${public_slug}`; the training share link and the settings page copy button both use that field. **[Certain]**
- Teams are created and renamed through `POST /v1/departments/:id/teams`, `PATCH /v1/teams/:id`, the onboarding wizard (same API) and the external sync (`services/sync/teams.ts`). **[Certain]**

## Decisions

### R1: Address segments and where each comes from

**Decision**: club = `organizations.slug`, department = `departments.slug`, team = `playerboard_settings.public_slug`, which now contains only the normalized team name (no department part, no UUID).

**Rationale**: Matches the spec assumptions. The department slug is already stable under rename, so a department rename no longer changes any address (FR-010 only requires an update "soweit sie in die Adresse einfließt"). Keeping the stored, trigger-generated team slug leaves the settings contract (`publicSlug`, `publicPath: null` when no address exists, US2 scenario 3) intact.

**Alternatives rejected**:
- Compute the team slug live from `teams.name` and drop the column. Deletes two triggers, but removes `publicSlug` from the contract and makes every team "have" an address, which contradicts US2 scenario 3 and widens the diff.
- Derive the department segment from `departments.name`. A rename would silently break shared links; the stable slug avoids that.

**Note**: `create_department()` normalizes without umlaut mapping, `playerboard_slug_part` maps `ä→a`, `ß→ss`. The two schemes differ for German names (for example "Fußball" gives department slug `fu-ball` but would give team-style `fussball`). The spec says to use the existing department slug, so this is kept and documented in ADR-014. **[Certain]**

### R2: Uniqueness of the last segment

**Decision**: add `authz.team_url_slug(name)` (wraps `playerboard_slug_part`, falls back to `mannschaft` when empty, truncates to 80 and trims a trailing hyphen) and a partial unique index on `teams (organization_id, department_id, authz.team_url_slug(name)) where archived_at is null`. Drop `unique (organization_id, public_slug)` on settings. The settings slug stays the output of the same function, so the index is the single source of uniqueness.

**Rationale**:
- FR-016 asks for the check "nach derselben Normalisierung, aus der das URL-Segment entsteht", at create and rename. An index on the same function cannot drift from the generator.
- Active-only matters: external sync retires a team and may later create a new one with the same name. A table-wide rule would make that insert fail every sync run. Un-archiving into a collision is rejected by the same index, which is the correct outcome.
- The old settings unique constraint cannot see `archived_at`; keeping it would make renaming an active team to a retired team's name fail. Resolution already filters `team.archived_at is null`, so a stale slug on an archived team cannot be reached. A pgTAP test pins this.

**Consequences**:
- Names that differ only after character 80 collide and the second is rejected. Accepted; team names are capped at 120 and real names are far shorter.
- The rule applies to all active teams in a club, including those without PlayerBoard settings. This is what FR-016 says. **[Certain]**
- **[Guessing]** An expression index calling a function in the `authz` schema must work when the inserting role is `authenticated`. PostgreSQL checks function privileges at index creation, not per row, so it should work. A pgTAP test inserting and renaming a team as `authenticated` verifies it. If it fails, make the function `security definer` or move it to `public`.
- `normalize()` must be immutable for index use. The existing `playerboard_slug_part` is already declared `immutable` and is used in a trigger; the index creation will confirm. **[Likely]**

### R3: One three-argument resolver, old functions dropped

**Decision**: replace `authz.playerboard_public_team(org_slug, team_slug)` with `(org_slug, department_slug, team_slug)` that joins `organizations.slug`, `departments.slug` (same organization, `archived_at is null`), `teams` by department (`archived_at is null`) and `playerboard_settings.public_slug`, then keeps the existing `module_enabled` and `public_sharing_allowed` checks. Create the six `public.playerboard_public_*` functions with a `department_slug` parameter and **drop** the old signatures explicitly.

**Rationale**: `create or replace` with a new argument list creates an overload, which would leave the two-segment lookup alive in the database. FR-008 wants it gone. A wrong department, wrong club or mismatching team all fail the same join and return no row (FR-004, FR-013). Explicit `departments.archived_at is null` covers the archived-department edge case rather than relying on `module_enabled`. **[Likely]** that `module_enabled` would already cover it; the explicit check removes the doubt.

`playerboard_public_team_info` additionally returns `organization_id, department_id, team_id` for the API. The function is `service_role`-only, the route parses the response into an explicit public schema, and the public payload stays unchanged.

### R4: Migration behavior on existing data

**Decision**: the migration starts with a preflight that raises one exception listing offenders, and changes nothing if any exist:
1. Active teams in the same department whose `team_url_slug(name)` collide.
2. Departments (with at least one team settings row) or their organization whose slug does not match `^[a-z0-9]+(-[a-z0-9]+)*$` or exceeds 200 characters, because the API and page reject such segments and the team would have no reachable address. Team slugs remain capped at 80 characters by the existing settings schema.

After the preflight: create function and index, replace the generator and drop the department refresh trigger and its branch, drop the settings unique constraint, rewrite `public_slug` for existing team rows by re-running the trigger (`update … set public_slug = public_slug`), then replace and drop the functions.

**Rationale**: auto-renaming collided teams or slugs would silently change user data and public links. An abort with a readable list is reversible and fixable by the operator. Switches, name formats and data toggles are not touched (FR-009, US4 scenario 4: no settings row is created, only existing rows are rewritten).

**Open check before merge**: run the preflight queries against production data. If they return rows, the operator has to rename or archive teams first. **[Guessing]** that none exist; this has not been checked. The migration file name must follow the pattern enforced by `scripts/check-migration-timestamps.mjs`.

### R5: Shared slug schema in `packages/contracts`

**Decision**: add segment-specific slug schemas (organization and department max 200; team max 80), `PublicTeamAddressSchema` (`orgSlug`, `departmentSlug`, `teamSlug`) and `publicTeamPath(address)` to `packages/contracts/src/playerboard.ts`. The API route params, the web route params and the settings path builder use them. The complete path is capped at 512 characters.

**Rationale**: the same regex is currently written in `public.ts`, `publicTeamPage.ts` and (as SQL) the table check. Three call sites for a three-part path justify one definition; `apps/*` may import `packages/*`. The middleware keeps its own anchored full-path regex, built from the same pattern string, because it matches a whole path rather than a parameter.

### R6: API routes

**Decision**: change the six routes to `/v1/public/playerboard/:orgSlug/:departmentSlug/:teamSlug[/trainings[/:trainingId]|/ranking|/veo|/photos]`. Remove the two-segment routes. `loadTeam` validates the three params with the shared schema, calls the info RPC once and returns the IDs; `loadTeamPresentation` takes those IDs and drops its own organization, settings and slug lookups.

**Rationale**: removes the lookup that matched settings by `public_slug` across the organization, which would be ambiguous once two departments can both have a team slug `u13`. That function is the one place where forgetting the department would leak another department's brand colors and season start, so it is covered by a dedicated test (R10).

Old two-segment API URLs get explicit retired-route handlers returning the same generic 404 body as an unknown address. They return no data and do not redirect (FR-008).

### R7: Web page, cache keys and middleware

**Decision**: move the page to `pages/mannschaft/[orgSlug]/[departmentSlug]/[teamSlug].vue`. Every `useAsyncData` key includes all three segments. `isPublicTeamPagePath` accepts exactly `/mannschaft/<slug>/<slug>/<slug>`; the length guard rises from 200 to 512 to cover a 200-character organization slug, 200-character department slug and 80-character team slug. The legacy two-segment path is handled as an explicit public 404 tombstone before authentication redirects; it does not serve data or redirect to the new path. Other malformed paths remain behind sign-in.

**Rationale**: with keys of the form `public-team-${orgSlug}-${teamSlug}`, two teams `u13` in different departments would share a payload cache entry on client navigation. That would show one department's team under another's address. The key change is the one non-mechanical edit in the page. The two-segment tombstone returns 404 for authenticated and anonymous users without revealing data; other malformed paths remain behind the existing sign-in middleware (FR-006, FR-008).

### R8: Team create, rename and sync

**Decision**:
- `POST /v1/departments/:id/teams` and `PATCH /v1/teams/:id` map PostgreSQL error `23505` on the new index name to `409 team_name_taken`. Un-archiving uses the same PATCH path. The web error-message table gets a German message for the new code.
- Sync (`services/sync/teams.ts`): if the batch insert or an update hits the index, fall back to per-row writes and record each offending row as an `invalid_record` pending conflict (field `name`, incoming value "Name kollidiert mit einer bestehenden Mannschaft") through `addUniquePendingConflict`, instead of throwing and failing the run.

**Rationale**: without this, the new constraint turns a sync run with one duplicate name into an aborted run. The per-row fallback reuses the existing conflict mechanism and keeps the happy path as one batch insert.

### R9: Recovery and rollback

The migration changes data (`public_slug` values, dropped constraint and functions). Old values are derivable from the old generator, which stays in `2026111701`. Rollback means a follow-up migration that restores the old functions, the settings unique constraint and the department refresh trigger, and re-runs the old generator; it is documented in ADR-014 but not shipped. Shared old links stop working by design (FR-008, ADR-013 already accepted this). No new logging is needed; the public routes keep the existing rate limit and uniform 404.

### R10: Test plan

- **pgTAP**: rewrite `playerboard_public_slug.test.sql` (team-only slug, no UUID, department rename leaves slug unchanged, team rename regenerates, collision rejected on insert/rename/un-archive, same name allowed in another department and another club, archived team does not block a new one, empty and umlaut names, 80-character truncation, insert as `authenticated`). Update the 3-argument calls in `playerboard_core`, `playerboard_api_support`, `playerboard_ranking_places`, `playerboard_veo_views`, `playerboard_veo_analysis`. Negative isolation: wrong department, wrong club, other department's same-named team, archived department, archived team, foreign training id, closed switch at each level, and a check that the old two-argument functions no longer exist.
- **API (Vitest)**: all six routes with the three-segment path; old two-segment path returns the standard 404; invalid, uppercase, over-long and `..` segments return 404 before any RPC; identical 404 body for unknown, closed and mismatching addresses; brand and season come from the resolved department's team when two departments share a team slug; settings `publicPath`; `team_name_taken` mapping; sync collision becomes a pending conflict.
- **Web (Vitest)**: `publicTeamPage.test.ts` positive and negative paths (legacy two-segment tombstone, 2 and 4 malformed segments, empty segment, trailing slash, uppercase, `..`, over-long); page and settings source tests renamed to the new file; async-data keys include the department; training share link contains the three-segment path and `?training=`.
- **Contracts**: schema and `publicTeamPath` tests.
