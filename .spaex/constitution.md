- Optimize for code that another developer can understand, verify, change, and remove safely. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Organize code around cohesive domain or feature boundaries where the codebase supports it. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer a change that clearly improves maintainability and correctness over theoretical perfection, and make the smallest reversible change that provides evidence about the next decision when a design is uncertain. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer early returns or named helpers when they make the main path easier to follow, reducing nesting. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Refactor repeated behavior when the shared rule is real and the abstraction makes both callers clearer, keeping the abstraction close to the domain that owns it. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Separate broad formatting or mechanical refactors from behavior changes when possible, because mixed diffs make review, debugging, rollback, and blame less reliable. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Treat a change of about 100 net lines as a useful review-size warning and a change approaching 1000 lines as a strong prompt to split the work or agree on the larger change in advance, identifying generated code, mechanical renames, and required migrations as legitimate exceptions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Treat smaller size thresholds as prompts for review rather than automatic failures, so that a function beyond roughly 40 to 60 lines, or nesting deeper than roughly three levels, gets a deliberate look at whether it is still one coherent unit. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- For any question about the codebase — what something does, where it lives, how pieces relate, which existing artifact might already satisfy a request, or how to trace a symptom back to its source, including exploratory lookups incidental to a larger task — build a bounded, task-specific context map first, before a raw `grep`/`rg` search or broad file reads: state the concrete intent as a question; choose a small token budget appropriate to the task, starting around 800–1500 tokens and increasing it only when the returned relationships are insufficient; run `graphify query "<intent>" --budget <N>`, using `--dfs` for a narrow dependency path and `graphify path` or `graphify explain` when the map needs one specific relationship or symbol; treat the result as a map by extracting the cited source locations, symbols, and relationships and then reading only the smallest source slices needed; and if the result is truncated or ambiguous, narrow the question or make one additional focused query rather than dumping the repository. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Preserve in the resulting context map, when available, the task intent and token budget, the selected files and symbols, the relevant edge or call relationship, source locations for every claim, and an explicit truncation or failed-consultation note; the map is a navigation aid, not a replacement for reading the source of a selected artifact, and it must not cause a full graph or full repository dump to be copied into the agent context. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Default all exploration to graphify before a raw grep, including a first look for a symbol or "where is X defined"; the only exemption is a local one-file edit at a symbol whose location is already known from earlier in the same task, and for authoring a new named artifact the graphify-first authoring rule still applies even when a context map would be unnecessary. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Interpret graph output against these rough thresholds, which are guidance rather than hard cutoffs and which operator judgment overrides: six or more identical lines with the same logic across candidates means extract and propose the refactor; fewer than five lines that are purely structural — setup, error-wrapping, adapter boilerplate — are often fine to leave rather than over-extract; and hits inside test files are usually left alone unless they are helper functions. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Leave duplicated arrange, assert, and setup blocks across test cases alone: they are often intentional signal, because each test's setup documents that test's assumptions in place and consolidating them can obscure regressions. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Prefer deletion over addition, boring over clever, and the fewest files possible; the shortest working diff wins, but only once the problem is understood, because the smallest change in the wrong place is not lazy, it is a second bug. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Question complex requests — ask whether X is actually needed or whether Y covers it. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Pick the edge-case-correct option when two standard-library approaches are the same size; lazy means less code, not the flimsier algorithm. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Do not be lazy about understanding the problem, input validation at trust boundaries, error handling that prevents data loss, security, accessibility, the calibration real hardware needs — the platform is never the spec ideal, a clock drifts, a sensor reads off — or anything explicitly requested. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_

## SHOULD_NOT

- Apply a blanket rewrite merely because an `ast-grep` pattern matches. _[from `com.github.haexmas.atoms.ast-grep/ast-grep-structural-search`]_
- Install a package automatically for `ast-grep`, or fail adoption of the molecule solely because the optional tool is absent. _[from `com.github.haexmas.atoms.ast-grep/ast-grep-structural-search`]_
- Assume that a platform-specific global or API exists in every runtime. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Catch an error merely to log and rethrow it unchanged, which usually duplicates logs and loses ownership of the failure decision. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Leave promises unhandled. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Replace repository tooling with a personal global installation. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Use `||` when a valid value such as `0`, `false`, or an empty string must be preserved, or hide a required value behind optional chaining without deciding how absence is handled. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Create circular dependencies or circular imports between modules. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.general-coding/general-coding`]_
- Introduce a barrel export, a pass-through module, a blanket re-export, or a new abstraction only to shorten an import path or to add a boundary that carries no meaning. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.general-coding/general-coding`]_
- Use mutation, shared mutable module state, or hidden global state as an accidental communication channel. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.general-coding/general-coding`]_
- Assume that a test file is discovered unless the runner configuration confirms it. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Leave floating promises in tests, or let a test pass before the asynchronous work it is meant to verify has completed. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Mock a unit's own logic so thoroughly that the test only verifies the mock wiring. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Turn every test into a slow end-to-end test. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Add artificial wrappers, blank lines, or extra files only to satisfy a line-count threshold. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Create folders only for superficial symmetry, such as putting every small class, interface, or helper in its own folder. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Enforce a universal maximum line count for functions, files, or pull requests, since domain complexity, cohesion, control flow, and the number of reasons to change are more meaningful. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Pad files up to the 500-line boundary or treat that boundary as a target. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Scatter one simple operation across many microscopic functions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Split a file solely to make it shorter. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Treat these defaults as a reason to reformat or reorganize an entire codebase. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Use comments to narrate code that could be made clear through structure and naming. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Do not rewrite existing duplicates already in the codebase, do not treat this principle as a replacement for human code review — borderline calls escalate to the operator, not to another agent — and do not require the graph to be complete or perfect, since a stale-but-present graph is still useful and the freshness backstop bounds staleness on tracked branches. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_

## MAY

- Existing projects may opt out of individual TypeScript strict checks during migration, provided the choice is made explicit. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- A language-required test-module declaration or registration may remain in a production file, while test bodies and test-only helpers live in dedicated test files. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Generated files, vendored code, snapshots, and other files not normally edited by hand may exceed the 500-line boundary and should be excluded from that assessment. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- The operator may suspend the graphify-first authoring rule for the current session with any natural-language request to that effect — for example "skip graphify check", "don't consult the graph this session", or "authoring rule off for this task" — honoring the intent rather than a specific phrase; the suspension applies only to the current session, must be re-issued in a new session, and does not exempt the agent from noting in its response which artifacts it would have flagged had the rule been active. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
